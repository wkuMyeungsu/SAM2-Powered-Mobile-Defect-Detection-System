main과 dev에는 GitHub 보호 규칙(ruleset protect-main-dev)이 걸려 있어서, 약속이 아니라 GitHub이 직접 막는다. 저장소 소유자도 예외가 없다.

막히는 일GitHub의 동작
main·dev에 직접 pushpush가 거부되고 GH013: Repository rule violations 오류가 나온다.
Squash, Rebase 병합병합 방식 목록에 Create a merge commit만 나온다.
force push, 브랜치 삭제거부된다.

실수로 로컬 dev에 커밋했다면 push가 거부된 상태에서 아래 순서로 옮긴다. 첫 줄은 지금 커밋을 그대로 가진 작업 브랜치를 만들고, 둘째 줄은 로컬 dev를 원격 dev와 같은 지점으로 되돌린다. 커밋은 작업 브랜치에 남아 있으므로 지워지지 않는다.

git switch -c feature/web/qr-page
git branch -f dev origin/dev
git push -u origin feature/web/qr-page

파트는 폴더 이름과 같다: web gateway preprocessing inference visualizer. 여러 파트의 폴더를 함께 바꿔야 하면 파트 자리에 common을 쓰고, 바뀌는 파트의 담당자 모두와 먼저 상의한다.

브랜치 이름은 항상 태그/파트/기능 세 단계로 만든다. feature/web처럼 두 단계로 끝나는 브랜치를 만들면 git이 feature/web/qr-page 같은 브랜치를 더 이상 만들지 못한다.

작업 위치 WORKSPACE

단위파트 1개 = 담당자 1명 = 폴더 1개 = 컨테이너 1개. 포트는 8000 + 파트 번호.
작업 범위코드·Dockerfile·의존성 파일 모두 내 파트 폴더 안에만 둔다. 다른 파트 폴더는 읽기만 한다.
실행내 폴더의 Dockerfile로 컨테이너를 만들어 실행한다. 저장소 루트에서 docker compose up --build <파트>. 호스트 PC에 직접 설치해 돌리지 않는다.
파트 간 호출컨테이너 주소로 HTTP 호출 (예: http://inference:8003). 컨테이너 안의 localhost는 자기 자신이다. 다른 파트 코드를 import하지 않는다.
데이터 형식파트 사이에 주고받는 형식은 구현 전에 docs/contracts/에 적고 양쪽 담당자가 확인한다.
공용 파일docker-compose.yml, .env.example, README.md, docs/는 저장소 담당자와 상의 후 바꾼다.

기록 기준 RECORD

브랜치 이름영문 소문자와 하이픈만. 이름만 보고 기능을 알 수 있게.
커밋 메시지<타입>(<파트>): <요약> — 타입은 태그 표의 커밋 타입.
예: feat(web): QR 접속 화면 추가
커밋 단위목적 하나, 동작하는 상태로. git add . 대신 파일을 지정하고, 커밋 전에 git status로 내 폴더 밖 파일이 없는지 확인한다.
PR 제목커밋 메시지와 같은 형식. 본문에 무엇을 바꿨는지, 어떻게 확인했는지.
PR 병합 방식Create a merge commit 만 사용. (Squash, Rebase 금지)

금지 사항 PROHIBITED

하지 않는 일대신 하는 일
main, dev에 직접 commit·push작업 브랜치에서 커밋하고 PR로 합친다.
내 파트 폴더 밖의 파일 수정공용 파일은 저장소 담당자와 상의한 뒤 바꾼다. 다른 파트 폴더는 그 담당자에게 요청한다.
호스트 PC에 의존성을 설치해 실행내 폴더의 Dockerfile에 적고 컨테이너로 실행한다.
git push --force, git reset --hard 등 이력을 지우는 명령잘못 올린 커밋은 git revert로 되돌리는 새 커밋을 만든다.
다른 사람의 브랜치에 push내 브랜치에서 PR을 올리거나 그 사람에게 요청한다.
비밀키, 토큰, .env, 모델 가중치(*.pt *.onnx) 커밋값은 .env에만 두고 .env.example에는 이름만 적는다. 이미 올렸다면 해당 키를 즉시 폐기하고 재발급한다.

처음 한 번만 한다. 저장소 담당자가 ADMIN을 끝낸 뒤에 팀원이 SETUP을 한다.

ADMIN
저장소 구성
저장소 담당자 1회 · SETUP보다 먼저
  1. GitHub에 빈 저장소를 만들고, 로컬의 main과 dev를 올린다. 
    git remote add origin https://github.com/wkuMyeungsu/SAM2-Powered-Mobile-Defect-Detection-System.git
git push -u origin main dev
  2. GitHub에서 설정한다.
    GitHub 설정값
    Settings → Collaborators팀원 GitHub 계정 초대
    Settings → Rules → Rulesets → New branch ruleset이름 protect-main-dev · Enforcement status Active · Bypass list는 비워 둔다 (저장소 소유자도 규칙을 따른다)
    Target branchesInclude by pattern으로 main, dev 추가
    Restrict deletions · Block force pushes켬
    Require a pull request before merging켬 · Required approvals 0 (PR은 거치되 승인 없이 작성자가 병합한다) · Allowed merge methods는 Merge만
    Settings → General → Pull RequestsAllow merge commits만 켬 (Squash, Rebase는 끔)
    Settings → General → Automatically delete head branches끔. 이 설정은 병합된 PR의 head 브랜치를 자동으로 지우는데, dev → main PR의 head 브랜치는 dev다. 작업 브랜치는 PR 병합 때 Delete branch를 눌러 직접 지운다.
SETUP
저장소 처음 받기
팀원 각자 1회
  1. GitHub 메일 또는 알림에서 저장소 초대(Collaborator)를 수락한다.
  2. 저장소를 받는다. 
    git clone https://github.com/wkuMyeungsu/SAM2-Powered-Mobile-Defect-Detection-System.git
cd SAM2-Powered-Mobile-Defect-Detection-System
  3. 작성자 정보와 pull 방식을 설정한다. 
    git config user.name "이름"
git config user.email "GitHub 계정 이메일"
git config pull.rebase false
  4. 브랜치 목록에 main과 dev가 있는지 확인한다. 
    git branch -a
  5. Docker Desktop을 실행한 뒤, 내 파트 컨테이너가 뜨는지 확인한다. 명령의 web 자리에는 규칙 탭 파트 표의 내 파트 이름을 쓴다. docker compose ps에서 상태가 healthy이면 완료다. 
    docker compose up --build -d web
docker compose ps

팀원 누구나. 기능·수정 하나마다 TASK 0 → TASK 1을 반복한다.

TASK 0
작업 브랜치 만들고 커밋하기
작업 시작 시
  1. 최신 dev에서 작업 브랜치를 만든다. 이름은 규칙 탭의 태그 표에 따라 <태그>/<파트>/<기능>으로 짓는다. 
    git switch dev && git pull
git switch -c feature/web/qr-page
  2. 내 파트 폴더(예: web/) 안의 파일만 고치고, 컨테이너로 실행해 확인한다. 
    docker compose up --build web
  3. 바뀐 파일을 하나씩 지정해 커밋한다. 커밋 전에 git status로 내 폴더 밖 파일이 목록에 없는지 확인한다. 
    git status
git add web/index.html
git commit -m "feat(web): QR 접속 화면 추가"
  4. 원격에 올린다. 처음 올릴 때만 -u origin <브랜치>를 붙이고, 그 뒤에는 git push만 쓴다. 
    git push -u origin feature/web/qr-page
TASK 1
작업 → dev (PR)
기능·수정 하나 끝날 때마다
  1. PR을 올리기 전에 dev의 최신 내용을 내 브랜치로 받아와 충돌을 내 PC에서 푼다. 
    git pull origin dev
git push
    충돌이 나면 충돌 파일에서 <<<<<<<부터 >>>>>>>까지를 남길 내용으로 고쳐 쓰고 마커 줄을 지운다. 그 뒤 git add <파일>, git commit, git push 순서로 실행한다. 병합을 취소하려면 git merge --abort를 실행한다.
  2. GitHub에서 PR을 만든다. base는 dev, compare는 내 브랜치(feature/web/qr-page)로 지정한다. 새 PR 화면의 base 기본값이 main이면 dev로 바꾼 뒤에 Create pull request를 누른다.
  3. PR의 Files changed 탭에서 바뀐 파일을 직접 확인한다. 내 파트 폴더 밖의 파일, .env, 모델 가중치(*.pt *.onnx)가 섞여 있으면 병합하지 않고 내 브랜치에서 빼는 커밋을 올린다.
  4. Create a merge commit으로 병합하고, 이어서 Delete branch를 눌러 원격의 작업 브랜치를 지운다. 승인 없이 작성자가 바로 병합할 수 있다.
  5. 내 PC의 작업 브랜치를 지운다. 
    git switch dev && git pull
git branch -d feature/web/qr-page

저장소 담당자. dev에서 전체가 동작하는 것을 확인한 뒤에만 한다.

TASK 2
dev → main (PR)
저장소 담당자 · dev 테스트 통과 후
  1. dev를 받아 전체를 실행하고 모든 파트가 healthy인지, 화면이 열리는지 확인한다. 
    git switch dev && git pull
docker compose up --build
    문제가 하나라도 나오면 이 TASK를 중단한다. fix/<파트>/<내용> 브랜치를 만들어 TASK 1로 dev에 먼저 고친 뒤, 이 TASK를 처음부터 다시 한다. main에는 문제가 해결된 dev만 올린다.
  2. GitHub에서 PR을 만든다. base는 main, compare는 dev로 지정한다.
  3. Create a merge commit으로 병합한다. Delete branch는 누르지 않는다. dev는 다음 작업에도 계속 쓰는 브랜치다.

병합 직후 GitHub이 "dev is behind main"이라고 표시한다. 병합 커밋 하나가 main에만 있다는 뜻이고, 다음 dev → main PR은 그대로 만들 수 있다. 이 표시를 없애려고 main을 dev에 병합하지 않는다.

위에서 아래로 시간이 흐르고, 한 줄이 사건 하나다. 작업 브랜치가 dev에 모이고 dev → main으로 올라간 뒤 같은 순서를 반복한다. 설명 앞의 검은 번호는 그 사건이 속한 TASK 번호다.
